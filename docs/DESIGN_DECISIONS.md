# Design Decisions

Short answers to "why is it like this?".

## Laptop backend, Firebase only stores
The webcam and the model live on the shop laptop, so the laptop does all processing. Firebase (free Spark plan) stores, authenticates and hosts. Cloud Functions and Cloud Storage need a paid plan, so they are not used. Trade-off: Scan Now works only on the shop laptop.

## Orders come from the camera, not the POS
Record Sale and Receive Stock only change the mock POS. An order is raised when the camera sees the shelf at or below `reorderLevel` for `REORDER_CONFIRM_SCANS` (2) scans in a row and no order is open for that part. Why: the shelf count is the verified truth; the POS can be wrong (that is what the mismatch alert is for). Two scans in a row stop one bad frame (a hand, a shadow) from ordering stock. Demo order: remove the part, scan twice, the order appears; then record the sale to match the POS.

## One order per part at a time
While an order is open, `lowScanStreak` is held at 0. After Received, the shelf must be low for fresh scans before the next order. This leaves time to restock.

## Cancel, never delete
Decided Nov 11, after a wrong order (a covered lens read the shelf as empty) could only be removed by editing the database. The shopkeeper can cancel an order before the dealer dispatches it, with a reason; it becomes **Cancelled** and stays in the list. Deleting was rejected: it would erase the history the dealer and Insights rely on, the dealer would see an order vanish with no explanation, and the rules could no longer promise that nobody deletes orders. A dispatched order cannot be cancelled, because the goods are on their way; it is received (returns are future work). A cancelled order no longer counts as open, so if the camera still sees the part as low a new order follows after the usual scans and delay; the confirmation message says so and points to Part Settings, rather than adding a hidden "do not reorder" flag. The dealer is notified only when an order they had accepted is cancelled (they may be preparing it); a cancelled Pending order simply leaves their queue. A dealer "Decline" is future work.

## Simulated parts for live testing
Decided Nov 11 (the user's idea). Some live cases cannot be run on real parts without moving real stock or real orders: both real parts had open orders, so "a cancelled order is followed by a new one" could not be tried on them. A `.env` setting, `SIMULATED_PARTS`, adds made-up parts to every scan as if the camera had counted them, and everything after detection runs unchanged. It lives in `.env`, not Firestore, so it cannot be switched on by accident or from a browser: it needs a restart, shows a warning in the log and is on the release checklist. Names must start with `zz_`, the prefix every test cleanup removes, and a simulated part can never change a count the model produced, so it can add test data but never fake real stock. Scan records are marked `simulated`.

## Least privilege per role (M10)
Decided Nov 11. The dealer is an outside business, so it reads purchase orders and nothing else: no stock counts, prices, sales log, alerts, scans or scanning settings. Orders therefore carry `productName`, written by the backend when the order is raised. The same applies to the laptop's API: a dealer's valid token is refused (403) for Scan Now and the shelf photo, because the camera and the image belong to the shop. The backend reads the role from `users/{uid}` (the same source as the rules) and keeps it for 5 minutes: the dashboard fetches the image after every scan, and a read per image would cost about 2,900 reads a day per open dashboard on the free plan. The trade-off is that a role change reaches the backend within 5 minutes, not at once.

## Mark Received is one transaction
`receiveOrder` changes the order state and adds the quantity to `posCount` together. A half-done receipt would leave stock and orders disagreeing. Receiving twice is refused. When two people act on the same order at once, the rules refuse the second write; the app then reads the order once to say what happened ("has already been received", "no longer exists") instead of a vague "could not be updated". Only an order that has not moved is reported as a permission problem.

## Reconciliation lives in two places
`backend/app/reconcile.py` persists status on every scan; `frontend/src/features/inventory/reconcile.ts` shows it live as the shopkeeper edits the POS. The rule is trivial (equal means Matched), and a live display needs it in the browser. Both have tests; change them together.

## Alerts: backend creates, browser acknowledges
One alert per mismatch, counts refreshed while active, Resolved automatically when the counts match. The browser may only do Open to Acknowledged with a server timestamp, so history cannot be rewritten from a browser.

## Notifications are derived, never stored
A notification exists while its alert or order needs attention, so nothing can go stale. Only the personal read keys are stored (`notification_reads/{uid}`). Unread (personal) and Acknowledged (shared) are different things. Reading never hides work counters.

## Part names come from the data
Product ids equal the model's class names. A new part is a retrain plus one document (NFR7).

## Detection guards
The model has no background class, so a person or room can score as a part. Boxes over 25% of the frame area or 60% of a side are dropped, and confidence is 0.5. The real fix is retraining with negatives.

## UI
Carbon-style look: IBM Plex, one teal accent, square hairline surfaces, status never colour-only. Tailwind and a dark theme were considered and dropped.

## Material UI, with the theme as the only source
Decided Oct 28: move fully to Material UI; new files stay TypeScript. Why: a standard, well-documented component library suits an enterprise-style app, and the new History and Insights pages (tables, filters, charts) can use MUI and MUI X Charts directly. How the look is kept: the theme sets radius 0, no shadows or ripple, IBM Plex and the one teal accent, so MUI matches the existing Carbon style. How it stays safe: screens use the shared wrappers (`Button`, `StatusBadge`, `FormField`, `NotificationMenu`), so each wrapper is converted on its own with the same props, and each task passes tests, axe and a screenshot comparison. Design values live once, in `frontend/src/shared/theme/tokens.ts`; the theme is built from them, and the CSS variables the existing stylesheets use (`--color-*`, `--space-*`, ...) are generated from the theme at runtime (`cssVariables.ts`), with colours and spacing pointing at MUI's own variables. So there is one source of truth and a half-finished move still looks consistent. `tokens.css` was deleted in MUI-2 rather than kept as a second copy; a test fails if any stylesheet uses a variable that is not defined. Page layout moved in MUI-13 to shared parts (`Panel`, `EmptyState`, `Page`, `CardPage`, the table parts) and to each component's own `styled`/`sx`, so screens no longer depend on CSS class names; MUI-14 (Oct 31) then moved the page-wide rules (reset, headings, focus ring, reduced motion) into `globalStyles.ts`, applied through MUI's `GlobalStyles`, replaced the last two utility classes with `Muted` and `VisuallyHidden`, and deleted `base.css` and the generated variables. There are no stylesheets left. Not MUI's `CssBaseline`: its defaults (font smoothing, body text size) would change the look. Final bundle: JavaScript 1,064 KB (327 KB gzipped) against 881 KB (264 KB) before the move; CSS 8 KB (the fonts) against 23 KB. The extra 63 KB gzipped is MUI and Emotion; code-splitting the main chunk is in the backlog. `NotificationMenu` stays a disclosure because MUI's Menu is an ARIA menu, the wrong pattern for a list of links. Trade-offs: 2 to 4 days of work close to the freeze, and a larger bundle (measured in the trial). A trial converts `Button` first as a go/no-go, and an Oct 31 stop date keeps it from delaying the feedback work.

## Stock changes are logged with the POS change
The supervisor asked for analytics on sales and received stock, but the POS buttons only overwrote `posCount`, so nothing recorded what sold or arrived. Every POS change now writes a `stock_movements` entry in the same transaction (Record Sale, Receive Stock, Adjust Stock, Mark Received). Why one write: a log that can drift from the POS would make the analytics wrong. How the rules enforce it: the product stores `lastMovementId`, the id of the entry created in the same write. A `posCount` change is refused unless that entry is new and its before and after counts match the change, and an entry is refused unless the product changes to match it. Entries record who (`by`, the signed-in user) and when (the server's time), and can never be edited or deleted, so the history is trustworthy. Each entry copies the part's cost and price at that moment, so a later price change never rewrites past revenue. The scripts that set counts directly (`demo_reset`, `seed_products --reset`) write a `Reset` entry the browser cannot write, which the analytics leave out. Trade-off: one more document per POS change, which is small on the free plan, and more rule checks (about 10 document reads per Mark Received, under Firestore's limit of 20).

## Adjust Stock instead of fake sales
Decided Oct 31. When the shelf and the POS disagree because stock was damaged, stolen or miscounted, the only way to make them match was Record Sale or Receive Stock, which would log sales that never happened and distort every sales figure. Adjust Stock sets the POS record to a count the shopkeeper made, with a required reason: Damaged, Lost or Stolen, or Miscount for fewer units; Found, Customer Return, or Miscount for more. The reasons feed the shrinkage figures in Insights, and a customer return counts against sales. The dialog starts at the camera's count but says the camera can miss parts facing away: if the camera is wrong, the right action is to rearrange the shelf, not to adjust. Customer Return is an adjustment rather than a separate button because returns are rare in this shop and the reason list keeps the screen simple. Trade-off: an adjustment is trusted; there is no approval step (owner and staff roles are future work).

## Part Settings: cost, price and reorder settings
The money figures (sales value, shrinkage value, stock value) need each part's cost and selling price, and the shopkeeper could not see or change the reorder settings that drive automatic orders. A Part Settings panel on the dashboard lists them, with the margin, and edits them in a dialog; the rules allow only those four fields plus who changed them and when. Cost and price may stay blank until known; anything that needs them then says "Not set" instead of showing 0. The currency is LKR, set once in `VITE_CURRENCY`. A reorder quantity of 0 turns automatic orders off for that part. Selling below cost is allowed (clearance) but warned about. Trade-off: the dealer can still read product documents, including prices, until M10 narrows the read rule.

## A delivery is counted once
A dealer delivery should be entered with Mark Received, which adds it to the POS and closes the order. If the shopkeeper also used Receive Stock for the same box, it would be counted twice. When a dispatched order exists for the part, Receive Stock now stops and says so, with a link to the Orders page and a Receive Anyway button for a genuine separate delivery. A warning rather than a block, because the shop can also buy stock elsewhere.

## Automatic scanning: time rules, dark frames and change-only writes
Decided Nov 4 after a shopkeeper's-eye review. Scanning every minute changes what "a scan" means, so four rules came with it. **Time, not scan counts:** an alert waits until a mismatch has lasted `ALERT_DELAY_SECONDS` (default 3 minutes), and an order until a part has been low for `REORDER_DELAY_SECONDS` (default 5 minutes) as well as for two scans in a row. Counting scans alone would let a customer walking to the till, a person restocking or a Scan Now pressed right after an automatic scan raise an alert or send the dealer an order; a time rule behaves the same however often scans run. The Stock Check row still shows a mismatch at once; only the alert, its notification and the order wait. The start times (`mismatchSince`, `lowSince`) live on the product, and a missing, malformed or future time counts from now, never from a guess. A timer must mean "mismatched (or low) the whole time we watched": on the first counted scan after the backend starts, and after a gap of more than 3 scan intervals with no counted scan (laptop asleep, backend stopped, frames too dark), the timers and the low-scan streak start again from that scan. Found live on Nov 5: a timer left from the day before opened two alerts on the first mismatched scan after a restart, and a part low before an overnight gap was ordered on the first scan after it. **Dark frames are skipped:** a dark shop reads as an empty shelf, which with automatic scanning would raise alerts and order stock every night; a frame below `MIN_FRAME_BRIGHTNESS` changes nothing, and Scan Now says to turn on the light. Measured on the shop laptop (Nov 4 to 5): lights on 171 to 183; lights off with daylight 40 to 53, counts still right; lens covered 18 and 39 (skipped). The minimum stays at 40: skipping a dim but valid frame is harmless, counting a dark one is not. Brightness cannot tell a hand partly over the lens (45.7, counted 0 and 0) from a dim shelf, so short obstructions are left to the time rules. **Change-only writes:** an automatic scan is saved to the history only when the counts change, plus a heartbeat every 10 minutes, and product statuses, alert counts and timers only when they change, so a quiet scan costs one write (`status/latest`, which must be fresh for the camera status line). This keeps the Spark plan's daily limits comfortable (about 1,500 writes and 7,000 reads a day from the backend) and turns the scan history into a clean time series for Insights: each record holds until the next, and a gap longer than the heartbeat means unknown, not unchanged. **One loop, one lock:** a background thread started and stopped with the app, sharing the scan service's lock with Scan Now; failures are logged and the loop carries on. The backend must run as one worker. Defaults keep it off (`AUTO_SCAN_ENABLED=false`), and delays of 0 restore the old instant behaviour for a demo. Trade-offs: alerts and orders arrive minutes later than a mismatch, and a long restock can still raise an alert (Pause Scanning covers that; see below).

## Staying responsive and honest about the camera
Decided Nov 4 to 11 from live measurements. **Camera kept open:** opening the webcam and discarding its warm-up frames took 1.25 s of every scan, about 70% of the backend's time; while automatic scanning is on, the camera stays open and each scan drops only the few stale buffered frames (capture 0.19 s). It is reopened once after a failed read and released when paused or stopped. Trade-off: the camera light stays on. **Bounded database calls:** a network hiccup held scans, and Scan Now behind them, for 19 to 144 s, because the Firestore library retries a failed read for up to 300 s and its `timeout` limits only each attempt; every call now has 5 s per attempt and 10 s in total, then fails as a storage error and the best-effort steps carry on. **Camera status line:** a dashboard that silently shows old counts is worse than none, so `status/latest` records every attempt (counted, skipped, failed, and the scanning settings), and the dashboard says which state it is in, always with an icon, text and a next step. "No Recent Scan" (nothing for more than twice the interval plus 30 s) is checked before the last outcome, so an old "all good" never hides a sleeping laptop or a stopped backend. Changes of state are announced to screen readers; the ticking age is not, and neither is the first state after the page loads (the line says "Checking Camera…" until both the status and the pause setting have arrived, so it never shows a wrong state for a moment). The backend also publishes whether scanning is on once at startup, without recording an attempt: otherwise the dashboard learned that scanning had been turned off only from the next scan, and with scanning off there may be none (found live on Nov 11; cost, one write per start). **Honest during the alert delay:** because an alert now waits 3 minutes, "no active alerts" no longer means "everything matches"; the dashboard summary counts the parts that differ with the same rule as Stock Check and says a lasting mismatch becomes an alert. It does not name the delay, which is a backend setting the browser does not read. **Scan Now keeps its place:** the main action stays at the right of the title whatever the status text's length, because a button that moves between states is hard to find. **Pause Scanning:** restocking takes longer than the alert delay whichever order it is done in, so the shopkeeper can pause automatic scanning for 15 minutes from the dashboard. It is stored in Firestore (`settings/scanning`), so it works from any device; the rules allow at most 30 minutes ahead, so it always resumes by itself; the loop reads it before each scan, and an unreadable setting counts as not paused, because a missed pause is safer than scanning silently stopping. The first scan after a pause starts the timers again (the gap rule).

## Alerts have their own page
Decided Oct 31. The dashboard's full alerts table repeated what Stock Check already shows (the same part, the same two counts), and acknowledged or resolved alerts disappeared from view, so there was no history to check. The Alerts tab now holds the work (open alerts, Acknowledge) and the history (when each alert was raised, acknowledged and resolved); the dashboard keeps a short summary of up to 5 active alerts, still acknowledgeable in one click. The page reads the alerts themselves, so there is no second copy that could go stale, and notifications stay derived. Open and acknowledged alerts come from the shared live listener, which is always complete; resolved ones come from a second, paged query (newest 50 by `createdAt`, Load More adds 50) that runs only while the Alerts page is open. Ordering by `createdAt` alone needs no Firestore index. When Load More widens the query, Firestore first answers from its local cache, which holds only the alerts already shown and would wrongly say "all loaded"; until the server has answered, a cached page that is not full is skipped. Counts that depend on unloaded history show "50+". A notification opens its alert's row (`/alerts?alert=ID`), highlighted and focused. Order history stays on the Orders page, and stock history becomes part of Insights, so the header stays at four tabs. Trade-off: one more page and query, and the dashboard shows at most 5 alerts.

## Two-row header below 960 px
Four tabs with count badges (Dashboard, Alerts, Orders, and Insights to come) do not fit beside the logo, bell, name and Log Out on a phone or tablet: at 390 px Orders was cut off. Below 960 px the tabs move to a full-width second row (measured: four tabs need 377 px of nav, which one row has from about 932 px); at 320 px all four fit. The nav scrolls rather than widening the page if it ever overflows, so a tab's focus ring is drawn inside the tab. Keyboard focus keeps the page order (home, tabs, bell, Log Out) at every width. Trade-off: the header is 45 px taller on phones and tablets. Every page also names itself in the browser tab title, after the unread count: "(2) Alerts · Smart Inventory".

## Business intelligence in the browser
Analytics (sales, shrinkage, days of cover, dealer lead time, reorder recommendations) are pure, tested functions (`features/insights/analytics.ts`) run in the browser over the last 7, 30 or 90 local calendar days. Why the browser: the data is already in Firestore and the hosted app must work without the shop laptop; Cloud Functions are not on the free plan. One shared loader (`InsightsProvider`) reads the stock change log and the orders once per session over a 180-day window with single-field queries (no index), so the dashboard tiles and the page cost the same 60-odd reads together. Definitions: sales are Sale entries net of Customer Return adjustments, each at its entry's own price (a price change never rewrites history; Reset entries are left out; unpriced units are counted and reported, never valued at 0). Shrinkage is Damaged and Lost or Stolen write-offs at each entry's own cost; Miscount, Found and returns are record corrections. Days of cover divides the camera's shelf count (the same count that drives ordering) by the period's average daily sales: an average, not a median, because the median of mostly-zero days is 0. Lead time is a median over received orders, because one slow order would skew an average, and it is dealer-wide since one dealer delivers every part. The suggested reorder level is lead-time demand plus a safety margin of half that demand (at least one unit), rounded up, and is withheld until a part has 14 days of history and the dealer 2 received deliveries, with the missing condition named. The dashboard tiles use a fixed 30 days and link to their section. Each chart has a table alternative; the Insights page is lazy-loaded (`@mui/x-charts` pinned to 9.17.0) so the main bundle does not grow. `scripts/insights_check.py` is a second, independent implementation of the same definitions, used to check the page live.

## Seeded demo history
Sales were never logged before F1, so the charts would start empty. `seed_history` writes about 30 days of demo data (sales, returns, write-offs, deliveries with their Received orders, a few Resolved alerts), every document marked `seeded: true` with an id starting `seedh-`, and removes only its own documents with `--clear`. It is planned backwards from each part's real POS count, so the chain of entries ends exactly at the count the product has now and the real log carries on from it; deliveries are placed where the stock had run low, as in real trading; a rerun overwrites the same ids. `demo_reset` keeps it, and all seeded orders and alerts are closed, so they never block automatic ordering. Seeded scan records were left out (only the deferred stockouts section would read them, and they would add thousands of documents). The Insights page shows "Includes demo data" when seeded records are in the period, and the report says the demo history is synthetic.

## Layers and errors
Routes, services, adapters; pure planners for decisions; typed `AppError`s in one envelope. After a scan is saved, reconciliation, alerts and orders each fail softly so a scan is never lost.
