# Testing

## Automated (run before any hand-off)
```bash
# backend (from backend/, venv on)
python -m pytest                      # 305 tests, fakes only
ruff check . && ruff format --check .

# frontend (from frontend/)
npm run typecheck && npm test && npx oxlint && npm run build   # 819 tests
```
Backend tests use fakes from `tests/conftest.py` (no webcam, no Firebase): a camera that returns a mid-grey frame (or a dark one, or fails), a detector, a repository that records every write and counts them as Firestore would, and a clock the test moves by hand, so time rules are tested to the second without waiting. `oxlint` matters: `tsc` skips `.js`/`.jsx`, and it caught a removed component still imported in `AppShell.jsx`.

Rules for live tests:
1. Snapshot the real data first; use clearly named `zz-*` temporary data; restore and verify identical afterwards.
2. Before testing anything that depends on a Firestore rule, read the deployed ruleset through the Firebase Rules API (service account) and compare it with `firestore.rules`.
3. Use a normal window and an incognito window for the two roles (one browser shares one sign-in across tabs).
4. Use port 5173 (backend CORS).
5. Python Firebase subprocesses can segfault when spawned from Node; use REST with a service-account token.
6. Do not run a snapshot and restore while someone is scanning: the restore would delete their scans. Check `status/latest.scannedAt` first. With automatic scanning on, use the `--keep-scans` restore. Pause scanning for the full regression: the loop resolves the `zz` alerts on its next matching scan.
8. Before a live test that needs the camera, check that it actually sees the shelf (the counts in `status/latest` match the shelf); twice it counted no parts with the shelf out of view. Open `backend/snapshots/latest.jpg` to see what the camera sees.
7. After a click that changes the URL, wait for the new state (for example `aria-pressed="true"`), not for the URL (and not for the next click: two filter clicks a few milliseconds apart lose the first, which no person can do): React Router renders a long table as a low-priority update, a few tens of milliseconds after the URL changes.

## Simulated parts (live testing without touching real stock)
Set `SIMULATED_PARTS=zz_name:count` in `.env` and restart the backend: every scan then includes that made-up part as if the camera had counted it, so reconciliation, alerts, orders, Cancel and the dealer's view run for real without moving real stock or real orders. Give it a `products/zz_name` document (POS count, reorder level and quantity) to steer the case: POS equal to the count with level 0 is "matched but low" (the order path); a POS different from the count is the alert path. Guards: the name must start with `zz_` (anything else stops the backend at startup with a readable message, seen live on Nov 11 with `brakepads:0`), it never changes the count of a part the model detects, the backend logs a TEST MODE warning, and scan records carry `simulated`. `sim_reorder_live.py setup|run|teardown zz_name` uses it to check that a cancelled order is followed by a fresh one only after the full delay; teardown removes the part's product, orders, alerts and log entries and strips it from scan records and `status/latest`. **Empty it after testing and at release.**

## Rules checks
`rules_test.py` (in `.handoff/live-tests/`, 65 cases) sends `firestore.rules` with mocked documents to the Firebase Rules API test endpoint, so a rule change is checked before the user publishes it and nothing is deployed or written. It covers the stock change log (every field, every type, the link to the product through `lastMovementId`, edits and deletes), Part Settings, who acknowledged and who received, and the unchanged rules. The service account needs the `firebaserules.rulesets.test` permission (for example the Firebase Rules Viewer role); without it the API answers 403.

## Rules attack checks
Over REST with real ID tokens, after the user publishes: a dealer cannot write products or acknowledge alerts; a shopkeeper cannot accept or dispatch; nobody can create or delete orders or alerts; a user cannot read or write another user's `notification_reads`; wrong timestamps are refused; a POS change without its log entry, a log entry by the dealer, and any edit or delete of a log entry are refused.

## Accessibility
axe-core run on each page and role at desktop and at 390 px, layout checked at phone widths 390, 375, 360 and 320 px, and review against the Web Interface Guidelines. The Oct 29 baseline found `scrollable-region-focusable` at 390 px: the table scroll boxes could not be reached by keyboard (desktop axe was 0). Fixed by the shared `TableScroll` wrapper, which becomes a labelled, focusable region only when the table overflows. Run axe at a phone width as well as desktop; some failures only appear when content overflows. Passing axe and "no sideways scroll" is not enough: on Nov 11 the user's own screenshots showed a button that changed place between states and a message that contradicted the table below it, both with axe 0. Look at a full-page screenshot of every state, and check focus after each keyboard action (a button that is disabled while saving drops focus in Chrome).

## Known flaky or limited
Detection can flicker on an unchanged shelf (for example 4 then 3); the two-scan rule absorbs it. End-on filters and dark rooms are missed. Latency compensation in Firestore updates the UI before the server confirms, so verify writes in the console too. In the regression the dealer's Received tile has twice (Oct 30, Nov 11) stayed stale for more than 15 s in the test browser although Firestore was right; a rerun on fresh `zz` data passed both times, and the cause is not proven (`regress.mjs` now logs how long the tile takes to catch up). A scan taken while the camera's view is disturbed reads 0 for every part at normal brightness; check `backend/snapshots/latest.jpg` before blaming the model.
